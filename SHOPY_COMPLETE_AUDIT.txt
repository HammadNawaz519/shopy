A. ARCHITECTURE OVERVIEW
================================================================================

1. Core Framework & Versioning:
   - Next.js: 14.2.24 (App Router)
   - React: 18.3.1 (React DOM 18.3.1)
   - TypeScript: 5.6.3 (Strict type checking, target: es5, lib: dom/esnext)
   - Runtime Environment: Node.js 20+ on Vercel Serverless Lambdas & Edge Middleware

2. Primary Application Layers:
   - Client Tier: Next.js Client Components ("use client"), Context Providers (Auth, Cart, Toast, AdminNotification), Vanilla CSS + Tailwind CSS 3.4.14.
   - Routing & Edge Tier: Vercel Edge Middleware (path matching `/admin/:path*`, `/account/:path*`), Next.js App Router (Static Site Generation / Incremental Static Regeneration / Dynamic Route Handlers).
   - API / Backend Tier: 31 Next.js Route Handlers (`app/api/*`) executing in Node.js Serverless Functions with connection pooling to PostgreSQL.
   - Persistence Tier (Single Source of Truth): Supabase Cloud PostgreSQL 15.8 (AWS us-east-1 pooler on port 6543, SSL enabled, node-postgres `pg` pool).
   - Coordination / Performance Tier: Upstash Redis REST API (`@upstash/redis` 1.38.2) for stampede protection mutex locks, distributed rate limiting, and short-lived versioned caching.
   - Media Pipeline: Sharp 0.35.3 image optimization pipeline, PostgreSQL `media_assets` table (bytea storage) & local Next.js `/api/media/[id]` edge cached endpoints.
   - Communications Tier: Nodemailer 9.0.5 with 3 dedicated SMTP channels (OTP/Security, Orders/Fulfillment, Support/Concierge) with RFC-5322 Message-ID alignment and anti-spam headers.
   - Enterprise Mirror: Google Sheets API v4 with Service Account JWT authentication and bidirectional webhook synchronization (`app/api/webhooks/sheets`).

B. COMPLETE REQUEST FLOW
================================================================================

1. Storefront Browsing Flow (Homepage):
   Browser
   → Vercel CDN (Edge Cache - 60s ISR)
   → [On Cache Miss / Revalidation]
   → Next.js Server Component (`app/page.tsx`)
   → `getCachedHomepageConfig()` + `getCachedCategories()` + `db.getProducts({ featured: true })`
   → Upstash Redis (`shopy:v4:homepage:config`, `shopy:v4:categories:all`, `shopy:v4:products:{"featured":true}`)
   → [If Redis Miss] → Supabase PostgreSQL (Port 6543 Pooler)
   → Next.js HTML Prerender
   → Browser Hydration
   → Browser executes client-side `useEffect` in `EditorialSection.tsx`
   → `fetch('/api/editorial/quote')` (Serverless Function invocation)
   → Groq AI / Gemini API / In-Memory Fallback Matrix
   → Browser DOM Update.

2. Product Detail Page Flow:
   Browser
   → Vercel CDN (5-min ISR / SSG Prerendered Route `app/product/[id]`)
   → [On ISR Revalidation]
   → Next.js Server Component
   → Upstash Redis (`shopy:v4:product:[cleanId]`)
   → Supabase PostgreSQL (`products` JOIN `product_images` subquery)
   → HTML Payload to Browser
   → Browser Hydration executes 2 client-side `useEffect` calls in `ProductReviewsSection.tsx`:
     a. `fetch('/api/reviews?productId=[id]&sort=newest')` → Redis/PostgreSQL
     b. `fetch('/api/reviews/eligibility?productId=[id]')` → PostgreSQL (`orders` & `order_items` verification)
   → Browser DOM Update.

3. Checkout & Order Placement Flow:
   Browser (`/checkout`)
   → Submits `POST /api/orders` with idempotency-key header & JSON payload
   → Vercel Serverless Function (`app/api/orders/route.ts`)
   → `getClientIp()` + `checkOrderRateLimit()` (Redis token bucket)
   → Idempotency Check in Redis (`shopy:v4:idempotency:order:[user/ip]:[key]`)
   → Zod Validation (`CheckoutSchema.safeParse`)
   → Concurrency Mutex Lock (`acquireDistributedLock('order:[idempotency/user]')`)
   → `db.recalculateCart()` (Authoritative server-side price lookup from PostgreSQL)
   → PostgreSQL Atomic Transaction:
     - `INSERT INTO orders`
     - Loop: `INSERT INTO order_items`
     - Loop: `UPDATE products SET stock_count = stock_count - qty, in_stock = (stock_count - qty > 0) WHERE id = $id AND stock_count >= qty`
     - [If any stock < qty] → ROLLBACK & throw error
     - COMMIT
   → Set Redis Idempotency Record (24h TTL)
   → Invalidate Catalog Cache (Version Bump / Cache Bust)
   → Background Side-Effects via `Promise.allSettled`:
     - `sendOrderConfirmationEmail()` → Nodemailer → Gmail SMTP
     - `sendAdminNewOrderNotification()` → Nodemailer → Gmail SMTP
     - `syncOrderCreated()` → Google Sheets API v4 (Orders + Order Items tabs)
   → Release Distributed Lock
   → HTTP 201 Response with `orderId` & `orderNumber` to Browser
   → Browser redirects to `/order-confirmation/[id]`.

4. Admin Status Update Flow:
   Admin Dashboard Browser (`/admin/orders`)
   → Submits `PATCH /api/admin/orders`
   → Vercel Serverless Function
   → `getAdminUser()` validates signed JWT session cookie (`shopy_session_id`)
   → Acquire Distributed Lock (`order:status:[orderId]`)
   → PostgreSQL Transaction:
     - `SELECT * FROM orders WHERE id = $1 FOR UPDATE` (Row-level lock)
     - Validate status transition & derive payment status
     - `UPDATE orders SET status = $1, payment_status = $2, order_history = ... RETURNING *`
   → Conditional Trigger:
     - If status/payment changed → `sendOrderStatusUpdateEmail()` / `sendPaymentReceivedEmail()` via SMTP
     - `syncOrderStatusUpdated()` via Google Sheets API
   → Release Distributed Lock
   → HTTP 200 Response.

5. Inbound Google Sheets Webhook Flow:
   Admin edits status cell in Google Spreadsheet
   → Google Apps Script `onEdit(e)` Trigger
   → HTTP `POST /api/webhooks/sheets` with header `x-sheets-secret: [SECRET]`
   → Vercel Serverless Function
   → `isSecretValid()` timing-safe comparison against `GOOGLE_SHEETS_WEBHOOK_SECRET`
   → `checkRateLimit()`
   → `processInboundSheetPaymentUpdate()`
   → Acquire Mutex Lock (`order:sheets-sync:[ref]`)
   → PostgreSQL `SELECT * FROM orders WHERE order_number = $1`
   → Enforce state transition rules (Prohibit REFUNDED->PAID, CANCELLED->PAID)
   → If rejected: Call Google Sheets API to revert cell to authoritative DB state
   → If accepted: `db.updateOrderPaymentStatus()`, dispatch customer email, log sync
   → Release Mutex Lock
   → HTTP 200 Response to Apps Script.

F. DATABASE QUERY PROBLEMS
================================================================================

1. Runtime DDL / `ensureTablesExist()` Anti-Pattern:
   - Location: `lib/db/store.ts` (lines 413-514, 2442-2500)
   - Problem: `ensureTablesExist()` and `ensurePaymentSchema()` execute `CREATE TABLE IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, and `CREATE INDEX IF NOT EXISTS` dynamically at runtime on every cold start or initialization.
   - Impact: In serverless environments, every new Lambda invocation executes heavy schema reflection queries, acquiring ACCESS EXCLUSIVE metadata locks on PostgreSQL tables and adding 200-500ms to cold start latency.
   - Fix: Migrate all table definitions and schema alterations to static migration scripts run once during deployment.

2. Unindexed JSONB Extraction Join in Admin Customers Query:
   - Location: `lib/db/store.ts` (`getCustomersSummary`)
   - SQL: `LEFT JOIN orders o ON u.id = o.user_id OR LOWER(u.email) = LOWER(o.shipping_address->>'email')`
   - Problem: The `OR LOWER(o.shipping_address->>'email')` predicate forces PostgreSQL into a sequential table scan of the entire `orders` table for every customer, ignoring the index on `orders.user_id`.
   - Impact: As orders scale into thousands, this query causes severe database CPU spikes and timeout risks.

3. Unpaginated Admin Queries:
   - Locations:
     - `getAllOrders()` (`SELECT * FROM orders ORDER BY created_at DESC`)
     - `getCustomersSummary()` (`SELECT ... FROM users ...`)
     - `getDiscounts()` (`SELECT * FROM discounts ORDER BY created_at DESC`)
     - `getAllReviews()` (`SELECT * FROM reviews ORDER BY created_at DESC`)
   - Problem: All admin list queries return unbounded result sets without `LIMIT` or `OFFSET` / cursor pagination.
   - Impact: High memory usage and slow serialization as database volume increases.

G. PRODUCT SYSTEM AUDIT
================================================================================

Product Data Flow:
Admin UI (`/admin/products`)
→ `POST /api/admin/products` or `PUT /api/admin/products`
→ Zod validation
→ `db.addProduct()` / `db.updateProduct()`
→ Category slug resolution from `categories` table
→ `INSERT INTO products` + `syncProductImages()` (Sequential ordering in `product_images`)
→ Invalidation of Redis caches (`shopy:v4:products:*`, `shopy:v4:product:*`, etc.)
→ Storefront SSR / ISR pages (`/products`, `/product/[id]`, `/collections/[category]`) serve updated data.

Audit Findings:
1. Category Linking: Products resolve `category_id`, `category_slug`, and `category_label` dynamically from the `categories` table on creation/update.
2. Variant Support: Colors are stored as JSONB `[{ name, hex }]` and sizes as string array `text[]`. Stock count is tracked globally per product (`stock_count`). There is no multi-dimensional SKU-level matrix (e.g. Size L in Charcoal having a distinct stock count from Size S in Ecru).
3. Slug Generation: Auto-generates URL-friendly slugs with automatic 4-digit timestamp suffixing on collision.

H. PRODUCT IMAGE SYSTEM AUDIT
================================================================================

Upload & Serving Lifecycle:
Admin upload file
→ `POST /api/admin/upload`
→ Sharp pipeline: Auto-orientation, resize to max 1400x1600 inside boundary, unsharp mask definition, WebP compression (quality: 86, effort: 4, smartSubsample: true)
→ Compressed buffer stored in PostgreSQL `media_assets` table (`bytea` column)
→ Returns media URL: `/api/media/[assetId]`
→ Served via `app/api/media/[id]/route.ts` with `Cache-Control: public, max-age=31536000, immutable`
→ Next.js `<Image>` component loads and optimizes the image.

Deletion & Orphan Handling:
- Product Deletion: Foreign key `product_images.product_id REFERENCES products(id) ON DELETE CASCADE` automatically deletes `product_images` metadata rows when a product is deleted.
- Image Storage Assets: Media binary records in `media_assets` are NOT deleted automatically when product image associations are removed (resulting in orphan records in `media_assets` over time).
- Recommendation: Add an admin garbage collection script or orphan cleanup hook to delete unreferenced `media_assets`.

I. CART & CHECKOUT SECURITY
================================================================================

1. Authoritative Recalculation (Zero-Trust):
   - Location: `lib/db/store.ts` (`recalculateCart`), `app/api/orders/route.ts`
   - Principle: The server recalculates all product prices, subtotal, discount codes, shipping fees, and final order totals by querying the database. The client cannot forge the final order amount.

2. CRITICAL VULNERABILITY FOUND — Client-Supplied Price Fallback:
   - Location: `lib/db/store.ts` lines 1348-1361 in `recalculateCart`
   - Code Inspection:
     ```typescript
     } else if (item.price !== undefined && Number(item.price) > 0) {
       const price = Number(item.price);
       const quantity = Math.max(1, item.quantity);
       subtotal += price * quantity;
       verifiedItems.push({
         productId: pid,
         name: item.name || "Product Item",
         price,
         quantity, ...
       });
     }
     ```
   - Vulnerability: If an item payload includes a `productId` that is NOT found in the database, `recalculateCart` falls back to trusting the client-provided `item.price`!
   - Threat Scenario: An attacker submits an invalid product ID with `price: 1` and `name: "Luxury Coat"`. The server accepts the item at Rs. 1 and creates an order for Rs. 1.
   - Fix Required: Remove the fallback completely. If `product` is not found in database, reject the item and abort calculation.

================================================================================
J. ORDER SYSTEM AUDIT
================================================================================

1. Order Creation & Concurrency:
   - Concurrency Lock: `acquireDistributedLock('order:[identifier]', 8)` prevents double-submit clicks.
   - Idempotency Cache: Requests with `Idempotency-Key` header are stored in Redis (24h TTL) and replayed idempotently.
   - Stock Decrement: Atomic SQL update: `UPDATE products SET stock_count = stock_count - $1, in_stock = (stock_count - $1 > 0) WHERE id = $2 AND stock_count >= $1;`. If `rowCount === 0`, the transaction rolls back immediately.

2. HIGH-PRIORITY BUG FOUND — Order Number Collision:
   - Location: `lib/db/store.ts` line 1465
   - Code: `const orderNumber = \`SHP-\${new Date().getFullYear()}-\${Math.floor(1000 + Math.random() * 9000)}\`;`
   - Problem: Generates only 4 random digits (1000-9999). Due to the Birthday Paradox, collisions occur within ~100-200 orders. Because `order_number` is UNIQUE in PostgreSQL, collision throws an unhandled constraint error and crashes order placement with a 500 error.
   - Fix Required: Generate a nanoid/crypto random alphanumeric string or use a PostgreSQL sequence (e.g. `SHP-2026-` + zero-padded sequence).

3. HIGH-PRIORITY BUG FOUND — Coupon Usage Limit Not Incremented:
   - Location: `lib/db/store.ts` (`createOrder`)
   - Problem: When an order is placed with an active promo code, `createOrder` applies the discount but does NOT execute `UPDATE discounts SET usage_count = usage_count + 1 WHERE id = $1`.
   - Impact: Promo codes with `usage_limit` can be used indefinitely without reaching their limit.

K. AUTHENTICATION AUDIT
================================================================================

1. Session Architecture:

2. CRITICAL VULNERABILITY FOUND — Hardcoded Default JWT Secret:
   - Location: `lib/security/session.ts` line 7
   - Code: `const JWT_SECRET = process.env.JWT_SECRET || "shopy_jwt_super_secret_key_change_in_production_2026_fashion";`
   - Problem: `.env.example` lists `SESSION_SECRET`, but `session.ts` checks `JWT_SECRET`. If `JWT_SECRET` is not explicitly set in Vercel environment variables, the system falls back to the hardcoded default secret.

3. CRITICAL VULNERABILITY FOUND — Registration Overwrites Existing Password Before OTP:
   - Location: `app/api/auth/register/route.ts` lines 149-160
   - Code:
     ```typescript
     let user = await db.findUserByEmail(normalizedEmail);
     if (user) {
       const updated = await db.updateUser(user.id, {
         name: name || user.name,
         passwordHash, // <--- Immediately updates DB with attacker's password!
         role: isAdminAccount ? "admin" : user.role,
         resetToken: generatedOtp,
         resetTokenExpiry,
       });
     }
     ```
   - Problem: If a user or admin is already registered, an unauthenticated attacker can submit `POST /api/auth/register` with that email and a new password. The server overwrites the user's password hash in the database BEFORE OTP verification! The legitimate user is immediately locked out.
   - Fix Required: If user exists, do NOT modify `password_hash` in `users` table during initial registration step. Only allow password changes via verified reset flows or require authentication.
